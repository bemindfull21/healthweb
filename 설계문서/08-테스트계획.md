# 테스트 계획

실제 스크립트는 [`../tests/`](../tests/)에 있다. 이 문서는 전략·커버리지 요약이고, 실행 방법은 [`../tests/README.md`](../tests/README.md) 참고.

## 1. 테스트 전략

- 별도 테스트 DB가 없다 — **운영 Oracle DB(SHINDB)에 직접 붙어서** 테스트 계정을 만들고, 검증 후 스크립트가 직접 지운다.
- 각 스위트는 독립 실행형 파이썬 스크립트(`urllib`로 API 호출 + `oracledb`로 직접 정리) — pytest 같은 프레임워크 없이 순차 `assert` + `print`.
- **절대 원칙**: 실사용자 계정(`bemindfull21`)과 그 데이터는 어떤 테스트 스크립트도 건드리지 않는다. 정리(cleanup) 함수는 항상 테스트 전용 login_id만 대상으로 한다.
- 회원가입 레이트리밋(5회/시간)이 인메모리라서, 스위트를 연달아 돌리면 이전 실행의 카운트가 남아있다 → **스위트마다 로컬 API 프로세스를 재시작**해야 한다.

## 2. 로컬 실행 준비

```bash
cd tests
cp .env.example .env        # HEALTHWEB_DB_PASSWORD 등 값 채우기 (.env는 git 미추적)
./run_local_api.sh          # 로컬 API 기동 (운영 DB에 연결됨 — 주의)

# 다른 터미널에서 (Pillow/oracledb 필요 — api/venv 사용)
../api/venv/Scripts/python.exe test_XX.py

# 다음 스위트 전에 반드시 run_local_api.sh 재시작 (레이트리밋 인메모리라 초기화 필요)
```

DB 자격증명은 스크립트에 하드코딩하지 않고 `tests/_db.py`가 `tests/.env`(git 미추적)에서 읽는다 —
이 저장소는 public이라 커밋 시 그대로 유출되므로 새 테스트 스크립트를 추가할 때도 이 패턴을 따를 것.

## 3. 현재 커버된 시나리오 (스위트별)

| `test_p2` | 팔로우, following/all 피드 스코프, 응원+댓글 알림, 응원 취소 시 알림 삭제, 자기행동 알림 제외, 챌린지 생성/참여/체크인/중복체크인 무시/나가기 |
| `test_p3a` | 리치 프로필(bio/link/location), 잘못된 링크 거부, 글 고정/해제(타인 글 고정 시도 차단), 검색(글/유저/챌린지), 양방향 차단의 전방위 효과(피드·프로필·검색·알림·팔로우 시도 403), 차단 해제 복구, 공개 챌린지 페이지 |
| `test_p3b` | 이미지 업로드/서빙, 비이미지·잘못된 kind·초과용량 거부, 아바타 설정, 글 이미지 노출, 남의 이미지 첨부 거부, 진행사진 share 강제, 미사용 미디어만 삭제 가능, 글 삭제 시 이미지 GC, 신고 생성+관리자 큐 조회+처리 |
| `test_push` | 텔레그램 연동 코드 발급/연결/1회용 소진/만료(404)/재배정(기존 연동 해제)/해제, 내부 API 키 검증(401) |
| `test_announce` | 비오너 403, 즉시/예정/만료 공지의 노출 여부, 종료일<시작일 거부(400), 알림 응답의 활성 공지만 노출, 수정 즉시 반영, 링크 정규화, 삭제, 커서 페이지에는 공지 미포함 |
| `test_rank` | 가입 직후 흑연(1), 연속 기록으로 점수 누적+등급 상승+승급 알림, 피드/프로필에 rank_level 노출, 챌린지 완주로 추가 상승, **기록 삭제해도 등급 하락 안 함**(핵심 불변조건) |

| `test_erp` | ERP 접근 권한 게이팅(미부여 403, 비오너 부여 시도 403), 오너의 권한 부여/회수, 영수증 업로드+실제 Gemini 추출 호출, 수동 저장(위안화+원화)+목록+합계, 상품명 빈 값 거부, 타 사용자 기록 삭제 불가(404), 본인 삭제 |

## 4. 배포 전 회귀 체크리스트

API(`app.py`)를 바꿀 때마다 최소한 다음 순서로 확인한다.

1. `node --check app.js` / `python -m py_compile api/app.py` — 문법 확인
2. 로컬 API 기동 후 `test_p1 → test_p2 → test_p3a → test_p3b → test_push → test_announce → test_rank → test_edit → test_kind → test_erp` 순으로 전부 통과(스위트 사이 재시작)
3. 프론트 UI 변경이 있으면 **브라우저로 직접 확인** — 자동화된 프론트 테스트가 없으므로 라이트/다크 모드, 실제 화면 스크린샷으로 눈으로 검증
4. 테스트 계정이 운영 DB에 남지 않았는지 `select login_id, name from healthweb.app_user` 로 최종 확인
5. 로컬 테스트용으로 바꿨던 API URL(`app.js`/`config.js`)을 원복했는지 확인 후 커밋

## 5. 커버 안 된 영역 (알려진 갭)

- **프론트엔드 자동화 테스트 없음** — Playwright/Cypress 등 E2E 프레임워크 미도입. 브라우저 확인은 매번 수동(또는 에이전트가 스크린샷으로 확인)으로 진행
- **부하/성능 테스트 없음** — 동시 사용자 시나리오 검증 안 됨
- **DB 마이그레이션 자체의 롤백 테스트 없음** — 마이그레이션은 적용만 검증, 되돌리는 경로는 스크립트로 존재하지 않음
- **텔레그램 실전송 검증 없음** — 로컬 테스트는 가짜 토큰(`000:faketoken`)이라 실제 메시지 전송까지는 확인 못 함, 실전 전송은 운영 배포 후 수동 확인
