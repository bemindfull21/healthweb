## 1. 프론트엔드 배포

프론트는 **자동 배포**다. 별도 빌드가 없으므로 push 즉시 원본 파일 그대로 나간다.

```bash
git add <변경 파일>
git commit -m "..."
git push
```

- GitHub Pages가 push 후 자동으로 반영 (보통 1분 이내 빌드, Fastly CDN 캐시 `max-age=600`이라 **실제 체감까지 최대 10분**)
- 반영 확인: `curl -s https://bemindfull21.github.io/healthweb/index.html | grep <확인할 문자열>`
- 정적 파일(이미지·아이콘 등)을 바꿨는데 URL이 그대로면 브라우저/CDN 캐시 때문에 안 바뀐 것처럼 보일 수 있음 →
  `?v=N` 캐시버스터를 파일을 참조하는 쪽 URL에 붙여서 강제 갱신 (아이콘 교체 시 실제로 이 방법을 씀)
- **`app.js`·`style.css`·`config.js`·`landing.js`도 동일** — 각 HTML(`app.html`·`index.html`·`challenge.html`·`about.html`·`install-guide.html`)에서
  `?v=N`로 참조 중(2026-09-12 도입, 파일별로 따로 버전 관리). **이 4개 파일 중 하나라도 바꾸면 참조하는 모든 HTML에서 그 파일의 `?v=`를 함께 올릴 것** —
  안 올리면 배포는 성공해도 사용자는 최대 10분(Fastly `max-age=600`) 넘게 옛날 코드를 계속 봄. 사용자가 "고쳤다는 게 반영이 안 됐다"고
  하면 제일 먼저 `curl -s https://bemindfull21.github.io/healthweb/app.js | grep <확인할 문자열>`로 실제 배포된 코드부터 확인하고,
  배포는 맞는데 화면에 안 보이면 캐시버스터 누락을 의심할 것.

## 2. 백엔드(API) 배포

프론트와 달리 **수동**이다.

```bash
# 1) 코드 전송
scp -i health-bot/ssh-key-2026-08-08.key \
    api/app.py api/requirements.txt \
    opc@168.107.89.8:/opt/health-web-api/

# 2) 의존성 설치 + 재시작
ssh -i health-bot/ssh-key-2026-08-08.key opc@168.107.89.8 \
  'cd /opt/health-web-api && ./venv/bin/pip install -r requirements.txt && sudo systemctl restart healthweb-api'

# 3) 헬스체크
ssh -i health-bot/ssh-key-2026-08-08.key opc@168.107.89.8 \
  'curl -s http://127.0.0.1:8000/healthz'
# 기대 응답: {"ok":true}

# 4) 최근 로그 확인 (에러 없는지)
ssh -i health-bot/ssh-key-2026-08-08.key opc@168.107.89.8 \
  'sudo journalctl -u healthweb-api -n 30 --no-pager'
```

**주의**: DB 스키마 변경이 있는 API 배포는 반드시 **DB 마이그레이션(3번)을 먼저** 적용한 뒤 API를 배포한다. 순서가 바뀌면 새 컬럼을 참조하는 쿼리가 배포 직후 실패한다.

## 3. DB 마이그레이션 적용

```bash
# healthweb 유저로 직접 접속해 SQL 실행 (oracledb 파이썬 스크립트 권장)
# scratchpad/try0NN.py 패턴 참고 — 문장을 리스트로 나눠 개별 실행
```

- 새 마이그레이션 파일은 `sql/0NN_설명.sql` 이름으로 추가하고 `CLAUDE.md`의 DB 섹션에 적용 여부를 기록한다.
- **`;` 단순 분리 방식의 일괄 실행 스크립트는 쓰지 말 것** — 파일 중간에 `--` 주석이 있으면 그 문장을 통째로 건너뛰는 버그가 있었다(`sql/040` 적용 때 발견). 문장을 파이썬 리스트로 나눠 하나씩 `cur.execute()` 하는 방식이 안전하다.
- 체크 제약(`check (col in (...))`)을 이름 없이 만들면 Oracle이 `SYS_C00xxxx` 같은 임의 이름을 붙인다. 나중에 값 추가하려고 제약을 찾을 때 `user_constraints.search_condition_vc`는 **원본 대소문자 그대로 저장**되므로 `upper()` 비교 없이 필터링하면 못 찾는다(`sql/043` 적용 때 실제로 겪은 문제).

## 4. 홈 화면 아이콘 재생성

```bash
cd health-web
./api/venv/Scripts/python.exe scripts/make_icons.py
# icon-512.png, icon-192.png, apple-touch-icon.png 갱신됨
```

색·모양을 바꾸려면 `scripts/make_icons.py`의 `GREEN`/`ROSE`/`M_SCALE`/좌표를 수정 후 재실행.
**파일을 바꿨으면 반드시 참조 URL의 캐시버스터(`?v=N`)도 올려야** iOS/Android의 홈 화면 아이콘 캐시가 갱신된다(파일만 바꾸면 기기가 계속 옛날 아이콘을 보여줌 — 실제로 겪은 문제).

## 5. 로컬에서 배포 전 검증

```bash
# API를 로컬에서 실사용 DB에 붙여 띄우기 (scratchpad/runserver.sh 패턴)
export DB_USER=healthweb DB_PASSWORD=... DB_DSN=shindb_low ...
./api/venv/Scripts/python.exe -m uvicorn app:app --port 8971

# 프론트가 로컬 API를 보게 임시 치환
sed -i "s#https://healthweb21.duckdns.org#http://127.0.0.1:8971#" app.js config.js
python -m http.server 8080

# 테스트 후 반드시 원복
git checkout config.js
sed -i "s#http://127.0.0.1:8971#https://healthweb21.duckdns.org#" app.js
```

- 로컬 서버가 **운영 DB에 직접 연결**되므로, 테스트 계정은 항상 스크립트로 정리한다. `bemindfull21`(실사용자) 계정·데이터는 절대 건드리지 않는다.
- 회원가입 레이트리밋(5회/시간)이 인메모리라 스위트 테스트마다 서버를 재시작해야 카운트가 초기화된다.

## 6. 장애 대응 체크리스트

1. `curl https://healthweb21.duckdns.org/healthz` 응답 확인
2. 응답 없으면 SSH 접속 → `sudo systemctl status healthweb-api`
3. `sudo journalctl -u healthweb-api -n 50 --no-pager`로 최근 에러 확인
4. DB 연결 문제 의심되면 wallet 만료·비밀번호 확인 (`_shared/secrets.env`)
5. 롤백이 필요하면: 이전 커밋으로 `git checkout <이전 SHA> -- api/app.py` 후 2번(백엔드 배포) 재실행
   — **VM에 이전 버전 백업본을 따로 두지 않으므로 git 히스토리가 유일한 되돌리기 수단**
